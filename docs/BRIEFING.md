후속 **3회 심층 검토**의 최종 구조·실패 반례·결정은 [아키텍처 결정](architecture/DECISIONS.md), 구체적인 착수 순서는 [구현 계획](development/IMPLEMENTATION-PLAN.md)을 따른다. 이 브리핑은 제품 개요다. 수집·운영·Plugin·UX의 상세 근거는 연결 문서에 나눠 관리한다.

## 1. 제안

**“오늘 놓치면 아쉬운 일과 다음에 접속할 이유를 한 화면에서.”**

DuckbillCalendar는 웹 공지 모음보다 **마감 중심의 개인 일정판**에 가깝다. 월간 달력에서 정액제 만료, 이벤트 참여 종료, 보상 수령 종료, 점검·패치와 PvP 기간을 함께 보고, 관심 항목만 작은 화면과 로컬 알림으로 가져온다.

권장하는 첫 버전은 **수동 이용권 + 검수된 공개 일정 피드 + 개인 메모 + 공개 PvP 기간 정보**다. 공식 웹사이트를 각 사용자의 게임 프로세스에서 직접 크롤링하는 구조는 채택하지 않는다. 수집기는 개발·운영 도구로 분리하고, 플러그인은 작은 정규화 JSON만 선택적으로 갱신한다. 네트워크를 끄고 번들 데이터와 파일 가져오기만 쓰는 경로도 제공한다.

이번 단계에서 확정할 수 있는 것은 화면·데이터 계약·개발 순서다. 계정 잔여 이용기간 자동 인식, 현재 전장 순환 기준점, PvP 시리즈 번호 자동 판독은 검증 전 기능으로 남긴다. 알 수 없는 값은 ‘미확인’으로 표시한다.

## 2. 핵심 사용자 흐름

1. `/dbcal`로 열면 오늘 종료되는 이벤트와 가장 가까운 이용권 만료를 먼저 본다.
2. 달력 날짜 또는 일정 행을 선택하면 오른쪽에서 참여 기간, 수령 기간, 확정 여부와 출처를 확인한다.
3. 관심 일정의 알림을 켠다. 이벤트 종료와 보상 수령 종료는 별도로 켤 수 있다.
4. 설정에서 계정 별칭과 실제 종료 시각을 입력한다. 만료일은 해당 계정 프로필을 쓰는 캐릭터에게 공유된다.
5. 작은 화면에서는 오늘 마감·다음 관심 일정·이용권 만료만 확인한다.

게임 실행 중 불필요한 이동을 줄이는 데 초점을 둔다. 참여 버튼 대신 **공식 페이지 열기**, 자동 가입 대신 **수동 체크**, 과도한 알림 대신 **관심 항목만 알림**을 기본으로 한다.

## 3. 요구사항과 우선순위

| 단계 | 포함 기능 | 완료 기준 |
| --- | --- | --- |
| P0 / 첫 사용 가능 버전 | 월간·목록, 종류 필터, 출처·확정 상태, 수동 개인 일정, 계정별 이용권 만료 | 인터넷 없이도 저장·재실행·수정 가능. 참여/수령 마감이 서로 다른 일정으로 표시됨 |
| P0 | 공식 공지·웹/시즈널 이벤트·할인·패치/점검의 검수 피드와 캐시 | 실패 시 마지막 정상 데이터 유지. 변경된 기간은 기존 ID를 보존해 정정 표시 |

| P1 | 검증된 전장 일별 순환, 필드별 규칙·참고 링크 | KR 클라이언트 임무 찾기와 여러 날 교차 확인. 패치 적용 범위와 기준점 기록 |
| P1 | 주간/일일 초기화, 주간 복권 등 반복 일정 | 한국 서비스의 개별 초기화 규칙을 출처와 함께 검증 |
| P1 | .ics 내보내기, 집사/가방 이용권, 캐릭터별 체크 목록 | 개인정보가 공개 피드로 섞이지 않고 내보내기 범위를 선택 가능 |
| P2 | 개인 시리즈 목표, 이벤트 완료 체크, 로그인 화면의 잔여기간 관찰 | 공개 API 또는 검증된 어댑터가 있는 기능만 채택. 읽기 실패는 수동 값을 보존 |

추가 후보는 하우징 추첨, 패션 체크, 레터라이브, 모그모그 컬렉션, 자유부대 행사다. 하우징·보상·완료 여부는 실제 상태 판독 없이 ‘완료’로 단정하지 않는다. 먼바다 낚시 등 Fisher와 중복되는 기능은 첫 범위에서 제외하고 나중에 사용자 클릭으로 연결한다.

## 4. 조사로 바뀐 설계

- **참여 종료 ≠ 수령 종료.** 공식 이벤트 목록에 두 기간이 함께 노출된다. 동일 이벤트에 두 단계의 기간을 둔다. [이벤트 목록](https://www.ff14.co.kr/news/event)
- **상대 종료 조건이 존재한다.** 마법자판 난타전처럼 패치 전까지인 항목은 날짜가 없는 상태로 저장한다. 달력의 특정 날짜 칸에 임의 배치하지 않고 ‘날짜 미정’ 목록에 둔다. [공식 이벤트](https://www.ff14.co.kr/events/fun/special/keybound_brawler)
- **나중 공지가 원문보다 먼저 정정될 수 있다.** 보상·기간 변경 공지를 별도 출처로 연결해 검토한다. 이벤트 목록만 주기적으로 읽으면 놓칠 수 있다. [기간 변경 안내](https://www.ff14.co.kr/news/notice/view/3153)
- **전장 회전은 고정 상수가 아니다.** 가이드는 0시 변경을 안내하지만, 실제 패치노트에는 주기 변경 이력이 있다. ‘3종 반복’ 같은 과거 전제를 제품 규칙으로 박아두지 않는다. [전장 가이드](https://guide.ff14.co.kr/pvp/sub04), [7.5 패치노트](https://www.ff14.co.kr/news/notice/view/2865)
- **시리즈와 CC 시즌은 다른 기간이다.** 추가 조사로 시리즈 12는 9/8 패치 7.56 이후 시작, 시즌 22는 11/10 패치 7.58 이후 시작임을 확인했다. 두 시작일을 달력에 별도 표시한다. 종료일·시즌 보상 수령 기한도 별도 단계로 표현한다. [7.56 패치노트](https://www.ff14.co.kr/news/notice/view/2947), [7.58 패치노트](https://www.ff14.co.kr/news/notice/view/3160)

## 5. 데이터 공급 방식 비교와 선택

| 방식 | 장점 | 비용·한계 | 판단 |
| --- | --- | --- | --- |
| 사용자가 모든 일정을 직접 등록 | 서비스 의존성 최소 | 매 사용자에게 입력 부담, 정정 전파 어려움 | 개인 일정·이용권과 비상용 |
| 플러그인이 공식 사이트 직접 수집 | 중앙 운영 없이 새 정보 접근 | 구조 변경·차단·이미지 안내·사용자 수만큼 요청 | 비권장 |
| 운영자가 JSON 수기 편집 | 초기 구축이 작고 판단 정확 | 누락·기간 정정의 운영 부담 | 첫 시드와 초기 운영 |
| 중앙 수집 + 검수 + 정적 피드 | 파서 수정 한 번으로 복구, 출처·정정 통일 | 검수자 필요, 게시 지연 | **권장** |
| 외부 커뮤니티 캘린더 의존 | 빠른 시작 가능 | KR 최신성·권리·종료 조건 신뢰 미확인 | 보조 제보만 |

초기에는 이 저장소의 `data/curated/`를 운영자가 편집하고 PR에서 검토한다. 수집 자동화는 후보 작성까지만 담당한다. 게시 데이터는 별도 `calendar-data` 브랜치에 두고 변경 불가능한 revision 파일과 manifest를 배포하는 안을 권장한다. 주소는 설계안이며 아직 생성·게시하지 않았다. 구체적인 수집 주기·수정 우선순위·장애 대응은 [데이터·운영 설계](DATA-DESIGN.md)에 있다.

## 6. 이용권 관리 원칙

공개 웹 데이터에는 개인의 실제 이용권 종료 시각이 없다. **계정 별칭 + 이용권 종류 + 종료 시각 + 마지막 수동 확인일**을 입력받는다. 게임 계정 ID·비밀번호·결제 정보를 받지 않는다. 기본 계정 1개를 만들고, 로컬 캐릭터와의 연결은 사용자가 명시한다. 정액제는 계정 범위, 개인 할 일은 캐릭터/전체 범위를 선택한다.

‘30일 추가’는 편의 도구로만 추후 제공한다. 보상 이용권·연장·환불 등으로 실제 종료가 달라질 수 있으므로 공식 계정 화면에서 확인한 종료 시각을 우선한다. 만료시각을 모르면 날짜 단위로 입력하고 ‘시각 미확인’으로 표시한다. 알려진 종료일에 무조건 23:59를 붙이지 않는다. 자동 연장이나 결제 기능은 포함하지 않는다.

## 7. 화면 방향

**Graphite + 옅은 금색 강조 + 종류별 점/문구**로 구성한다. Fisher의 Graphite/Paper 팔레트와 작고 읽기 쉬운 정보 밀도를 참고했다. 대형 홍보 이미지보다 종료 시각과 출처가 눈에 들어오는 정보 화면으로 만든다.

주 화면은 상단 가로 탭, 중앙 월간/목록, 우측 선택 상세다. 좌측 메뉴와 전장·PvP 탭은 제거하고, 오늘·내일 전장 이름을 달력 하단 한 줄에 표시한다. 시즌·시리즈 시작은 날짜 항목과 시작일 바로가기로 제공한다. 이벤트 표시는 `기간 막대`와 `시작·종료만` 중 선택하고 저장한다. 큰 요약 카드를 한 줄로 줄이고 본문 여백과 행 높이를 압축했다. 좁으면 상세를 아래로 쌓는다. Dalamud 이식 목표는 기본 980×660, 최소 760×500이다.

목업에 공지 목록·필터·일정 선택·월 이동·관심 알림 선택·수동 입력·이용권 수정·테마·오프라인 상태 전환을 구현했다. 수집 후보 검수는 로컬 상태 변경과 JSON 내보내기까지만 제공한다. 브라우저 자동 제어가 차단돼 실제 클릭·렌더링 검증은 미완료다. 실제 GitHub PR 작성과 피드 게시, 인게임 소리 알림은 아직 구현하지 않았다.

## 8. 기술 구조와 Fisher 재사용

```text
Official public pages → Collector → Candidate records → Human review
                                                     ↓
                                       Schema + semantic validation
                                                     ↓
                                      Versioned JSON + manifest
                                                     ↓ (optional HTTPS)
Core ← Feed/cache adapter ← Plugin UI / local notifications
  ↑                           ↑
Rules & clock             Personal JSON / account profiles
```

권장 디렉터리는 `src/DuckbillCalendar.Core`, `src/DuckbillCalendar.Plugin`, `tools/CalendarDataImport`, `data/curated`, `data/schemas`, `docs`다. Core에 기간 모델, 확정 상태, 반복 규칙, 알림 중복 방지, 데이터 병합을 둔다. Plugin에 Dalamud 서비스, ImGui UI, 캐릭터 연결과 비동기 HTTP·파일 어댑터를 둔다. 웹 요청·파일 IO·긴 범위 계산을 Draw에서 하지 않는다.

참고한 Fisher revision은 `a2b223b646aecf0897c6c1a3b0610a5921d45d41`이다. `src/DuckbillFisher.Plugin/UI/MainWindow.cs`, `UI/Themes/UiThemes.cs`, `UI/UiScale.cs`, `docs/development/ARCHITECTURE.md`, `AGENTS.md`를 확인했다. 해당 체크아웃의 프로젝트는 Dalamud SDK 15.0.0 / API 15다. 이것을 신규 프로젝트의 영구 최신 버전으로 단정하지 않고 실제 착수 시 KR·글로벌 참조를 다시 확인한다.

재사용 후보는 테마·배율 적용 방식, 안정적인 ImGui ID, 한국어/영어 리소스 분리, Core/Plugin 경계, 설정 원자 저장·백업, 로컬 알림 수명 관리다. 낚시 계산·게임 판독은 복사할 필요가 없다. Fisher에는 런타임 HTTP 금지라는 프로젝트 자체 방침이 있다. Calendar는 원격 공개 피드가 핵심인 별도 프로젝트이므로 **명시적인 선택 갱신과 오프라인 모드**를 새 경계로 제안한다. Fisher의 파일과 규칙은 수정하지 않았다. 실제 코드를 옮길 때는 Fisher의 AGPL-3.0 및 관련 고지 조건을 유지한다.

## 9. 개발 계획과 출시 판단

1. **1차: 오프라인 골격.** 기간·상태 모델, 수동 이용권·개인 일정, 한국시간 달력·목록, 영속화. 합격: 월/연 경계·날짜 미정·잘못된 시각을 구분하고 재실행 보존.
2. **2차: 정적 피드.** 검수 파일·검증기·manifest·HTTP 캐시·마지막 정상본. 합격: 장애·빈 결과·파서 변경에서 정상 데이터를 지우지 않음.
3. **3차: 로컬 알림·작은 화면.** 계정/캐릭터 연결과 알림 중복 방지. 합격: 캐릭터 전환·재로드·재접속의 중복/유실 시나리오 확인.
4. **4차: 공개 PvP 정보와 제한된 순환.** 기간 카드부터 추가. 순환 예측은 KR 임무 찾기와 기준점 검증 뒤 개방.
5. **5차: 운영 자동화.** HTML 후보 수집·정정 비교·검수 편의. 합격: 운영자 부재·수집 실패·급한 일정 정정을 수동 경로로 처리 가능.

3회 검토 후 운영·장애 시험을 포함한 추정은 1인 기준 약 4~7주로 수정했다. UI 완성도·KR 실기 환경·수집 정책 확인에 따라 늘 수 있으며 납기 확약이 아니다. 먼저 오프라인 P0를 완성하면 사이트 접근이 막혀도 제품을 사용할 수 있다. 1주 운영 파일럿에서 누락·정정 소요·수동 검수 시간을 측정한 뒤 갱신 주기를 조정한다.

초기 운영 목표는 하루 2회 검수, 패치일 추가 검수다. 수집 2시간/클라이언트 1시간+0~10분 jitter를 제안하며 6시간은 선택 저빈도 모드다. 검수 대기까지 합치면 정상 시나리오에서도 약 15시간 10분의 대기가 가능하고 장애 시 상한은 없다. ‘수집 성공 시각’과 ‘운영자가 내용 확인한 시각’을 별개로 보여준다. 긴급 점검의 실시간 경보기로 홍보하지 않는다.

## 10. 구현 전에 남은 검증

- 공식 사이트의 공개 HTML 수집·요약 재배포 허용 범위. robots.txt가 오류 화면으로 이동하므로 허용의 근거로 쓰지 않는다. 허용 범위가 불명확하면 수기 등록·원문 링크만으로 시작한다.
- 전장의 KR 0시 경계, 적용 패치별 순서·기준점·중단일. 가이드의 전체 필드 목록을 곧바로 실제 회전 목록으로 취급하지 않는다.
- 신규 시리즈·시즌의 시작·종료 발표를 지속 확인한다. 시리즈 12 시작과 상대 종료 조건은 확보했다. 글로벌 달력을 한국 서비스 일정으로 대체하지 않는다.
- Dalamud 정책은 PvP 기능을 폭넓게 제한한다. 공개 기간·정적 규칙만 다루고 전투 중 추천·적 정보·전술 보조는 범위에서 제외한다. 그래도 공식 저장소 허용은 미확정이며, PvP 부분은 분리해 심사 방향 확인 후 배포 범위를 결정한다. [공식 제한](https://dalamud.dev/plugin-publishing/restrictions/)
- 계정 종료기간 자동 판독의 실제 가용성. 검증된 공개 API가 없다면 수동 입력을 유지한다.
- 게임 안 폰트·DPI·창 축소·현지화·로그아웃/재로드·패치 직후 Dalamud 비가용 상황. HTML 확인은 인게임 검증을 대신하지 않는다.

## 11. 이번 전달물

브리핑·출처 조사·데이터 운영 계약·화면 명세와 HTML 목업을 작성했다. 공개 일정 6건에 참여/수령, 상대 종료, 점검, CC 시즌과 PvP 시리즈를 담았다. 후속 요청에 따라 상단 탭·기간 표시 전환·오늘/내일 전장·시즌/시리즈 시작일과 컴팩트한 배치를 반영했다. [검증 범위와 재현 동선](VERIFICATION.md)을 참고한다.
